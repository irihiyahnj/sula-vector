用户要求跳出现有设计、只对准目标给出建议。这是建议，尚未采纳。

目标：换任何模型、任何时间接手，开机就知道规矩；想知道为什么，查得到。

本会话三组实验支持的事实：开机时读到规矩本身才有用（约束题闭卷 6/14 升到 12/14）；原因不必开机读，查得到即可（加查阅 24/24）；门禁与证据机制对接手没有贡献。sulacompany 444 条在force判断中，有 121 条正文几乎只重复标题，其中 120 条是为结清未认领捕获而写——门禁要求「有原因」，得到的是凑数的原因。

建议：
1. 规矩清单：一个片段，按主题组织，每条一句能照做的话。改规矩就追加一版完整的新清单，新版 supersedes 旧版；写入工具打印本次增删了哪几条，使删除成为看得见的动作。开机内容 = 最新清单 + 未完成目标 + 最近几条日志标题 + 一行查阅方法。两版并存时开机内容同时显示两版并提示合并，不静默丢失。
2. 决定日志：现有 fragments，只追加，写决定与原因，按需搜索。不再要求为每次文件变化写原因；单次改动的原因写在 commit message 里。
3. 文件变化交给 git；不用 git 的文件夹可保留 witness 作可选工具，不进门禁。
4. 删除：unexplained-change 门禁、捕获图与验证绑定、decay、review、scheduler、llm-dispatcher、auto-update、thread/family/cadence 等字段与视图；Tier C/D/E 不再分发给采用方。

Tier A 仍成立：清单本身是片段，只追加，开机内容仍是 render(fragments)。

相对于「每条规矩一个片段、标题写规矩句」（已验证 12/14）：清单在每次修改时让作者看到全部规矩，过时规矩集中在一处而不是散在数百行里；去掉占开机内容约 21% 的片段 id；可以按主题而不是按时间组织。这一点尚未验证。

未验证：清单会不会被持续维护；清理过时规矩后的实际大小；模型重写整份清单时漏掉规矩的频率。

验证办法（只读）：让模型把 sulacompany 的 141 条规矩句合并、去掉被推翻的、按主题整理成第一份清单；测大小；用原 24 题加一套新题闭卷与查阅各测一次；由用户判断这份清单能否直接交给新人。约束题不低于 12/14 再改工具，先用于 sula-vector 自身，再逐个项目迁移。
